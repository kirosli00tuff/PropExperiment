### How the bound works (mdio/bounded.py)

The bound is a trade date. It is ctx.last, the read window's last trade date.

1. **A store whose name starts after the bound is never opened.** No hash, no metadata, no row is read from it.
   base_rules.store.refuse_path still runs on its path first, so sealed, research, MES and foreign paths are
   refused even when the store is skipped. In E.23's discovery read, all four step 2 stores (first date
   2019-05-06) are skipped this way.
2. **Every other store passes the frozen input checks unchanged** (`base_rules.store._checked_input`: path,
   sha256, metadata, plan window, hist calendar). Plainly: the sha256 streams the whole file's bytes through
   the hash, but no row is decoded by it.
3. **Rows are read per parquet row group with `ParquetFile.iter_batches`.**
   - A row group whose trade_date statistics put every row after the bound is never decoded (pruning).
   - Every decoded batch (at most 65,536 rows) is filtered to trade_date <= bound in Arrow before anything
     reaches pandas.
   - Plainly: inside a row group that straddles the bound, the bound is a post-decode truncation. Later rows
     are decoded batch by batch and never kept. Across row groups it is true pruning.
   - In the E.23 replay no row group straddled the bound. The ext2010 stores end on 2019-04-30, so all 3 of
     each store's row groups were read whole.
4. **The kept rows then go through the same checks base_rules.store.read_era runs:** the frozen booking checks,
   the 2024-02-29 refusal, and the splice and blackout check. Then the bound is **asserted** by `check_bound`:
   no label and no booked date may fall after the bound, else `BoundBreached`. A final check runs on the
   assembled bars as well. `BoundBreached` is deliberately not a StageEBarRefusal, so `load_or_exclude` never
   turns a breach into an exclusion; the run stops.
5. **The bars are assembled as load_product assembles them.**
6. **Known limit:** rows after the bound inside a store that *is* loaded are never checked, because the
   bounded read never looks at them. A full read of the same file would check them.

### Book files (mdio/book_files.py, mdio/trigger_books.py)

- **Layout.** `per_root_record` uses E.21's `stage_e21_per_root/1` layout: root, vehicle, tick_value_cents,
  per_contract_daily_dollars, holdings, fills, counters. Holdings and fills are multiday.book's own
  BookResult rows, keyed by book id. Two keys are added: `units` (one row per unit, ISO dates) and
  `book_counters`.
- **Schema name.** `schema` is `mdio_per_root/1` and `layout` names E.21's. A test checks the shared keys
  against `multiday.evaluate._root_rows` field by field.
- **Writing.** `write_per_root` writes `<out_dir>/per_root/<ROOT>.json` once (O_EXCL).

## 5. Could not do, or for the lead

- **Fable review (A2) is pending.** It is the lead's to route. This worker did not spawn it.
- **The bound is not wired into the frozen runners.** multiday/run.py and trigger_hold/run.py are pinned, so
  they still load unbounded if rerun. Any future multi-day stage must build its runner on
  `mdio.bounded.bound_context` + `check_bounded`, and write books through `mdio.book_files` or
  `mdio.trigger_books`. This follows from the pins; it is not a gap in the fix.
- **Straddling row groups are decoded, then truncated** (section 2, item 3). Parquet does not allow less
  without assuming row order inside a group. Row groups in the real ext2010 stores hold about 1M rows (about
  3 years). A future read whose bound falls mid-store will decode, and drop, up to one row group of later
  rows. The replay did not exercise that case on real data; only the synthetic tests did.
- **Pruning trusts each loaded file's footer statistics**, and the file's bytes are pinned by sha256. The
  bound assertion catches any kept row after the bound. A group pruned on wrong statistics would be missed
  silently, but only if those statistics were wrong in a sha256-pinned file.
- **mdio/ is a new top-level package not listed in any freeze or harness manifest.** If the lead wants it
  frozen for the next multi-day read, that stage's freeze should list mdio/*.py and tests/test_mdio_*.py.
